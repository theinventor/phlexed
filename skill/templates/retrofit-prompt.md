## Core principles

1. **ONE view per iteration.** Never batch multiple conversions in one commit. Each
   iteration converts exactly one template or partial and commits atomically.
2. **Preserve ALL existing behavior.** The page must render identically after
   conversion. Do not "improve" the markup. Do not drop accessibility attributes.
   Do not silently change element semantics.
3. **Components from the registry, always.** If a pattern in the source template maps
   to a registered component, use the component. Full namespace: `{{NAMESPACE}}::Button`,
   not `Button`.
4. **Props, not CSS classes.** Use the library's prop DSL. Do not pass raw class
   strings where a prop exists.
5. **Follow batch order strictly.** Shared partials (batch 1) must be converted
   before the views that depend on them. The fix_plan.md is already ordered this way
   — do not skip ahead.
6. **Atomic commits per conversion.** Each successful conversion gets its own commit:
   `retrofit: convert <relative/path> to Phlex`. Failed conversions get skipped and
   logged — never partial commits.

## Iteration workflow

Every iteration follows these steps:

### Step 1: Pick the next task

Read `.phlexed/retrofit/fix_plan.md`. Find the first task that is not marked complete
(`- [ ]`). If no unmarked tasks remain, stop with `STATUS: COMPLETE`.

Never reorder. Never skip ahead unless a task is explicitly blocked by a failed
prerequisite.

### Step 2: Read the source template

Read the full contents of the source template file. Understand what it renders,
which locals it uses, which partials it includes, which helpers it calls.

Run `git log -- <path>` to see recent changes (if any). Do not convert a file that
has uncommitted changes — warn and skip.

### Step 3: Check prerequisites

If the task has dependencies (other templates listed as "depends on"), verify each
is already marked complete in fix_plan.md. If any prerequisite is not complete, skip
this task and move to the next one. Log the skip.

### Step 4: Plan the target Phlex class

Sketch the view class structure before writing code:

- **Class name:** `ResourceActionView` (Rails convention: `SettingsIndexView`, not
  `SettingsIndex`). For partials, use the new_components_needed suggestion from the
  plan, or derive from the filename (`_sidebar.html.erb` → `Sidebar`).
- **Inheritance:** whatever the project uses. Grep existing Phlex files for the base
  class. Default to `Views::Base` if detection fails.
- **File path:** Rails+Phlex convention puts view classes under `app/views/<resource>/`
  using the same path structure as the original template. A partial becomes a
  component in `app/components/` (or wherever existing components live).
- **Props / initialize:** every instance variable the original template uses (`@user`,
  `@items`) becomes a `initialize` kwarg. Every local passed via `render locals: {...}`
  becomes a kwarg. No globals.

### Step 5: Generate the Phlex class

Write the class. Rules:

- Use `render {{NAMESPACE}}::Component.new(...)` for every registered component.
- Use the library's prop DSL (`variant: :primary`, `size: :lg`), never raw classes.
- Block content goes in `do ... end` blocks, not string props.
- Rails form builders still work — use `form_with` inside Phlex blocks with `plain`
  to emit the form helper output directly.
- Preserve `data-*` attributes (Stimulus controllers, Turbo attributes) verbatim.
- Preserve all accessibility attributes (`aria-*`, `role`, `alt`, `for`).
- For complex helper chains (`number_to_currency`, `time_ago_in_words`), call them
  inline using `helpers.number_to_currency(@total)`.

If the plan's new_components_needed list says this task needs a new Phlex component
(e.g., converting `_sidebar.html.erb` to `Sidebar`), invoke `/phlexed-component`
first, then continue the conversion using the newly created component.

### Step 6: Update the controller

If converting a top-level view (not a partial), update the controller action to
render the Phlex class:

```ruby
# Before
def index
  @users = User.all
end
# Rails picks up app/views/users/index.html.erb implicitly.

# After
def index
  @users = User.all
  render UsersIndexView.new(users: @users)
end
```

Pass instance variables as kwargs. If the controller has no action file change
needed (shared partial conversions), skip this step.

### Step 7: Preserve the original template

Rename the source file with a `.pre-phlex` suffix so the user can compare
before/after during review:

```bash
mv app/views/users/index.html.erb app/views/users/index.html.erb.pre-phlex
```

Do not delete. The user cleans up `.pre-phlex` files in a final pass after verifying
the conversion.

### Step 8: Run tests

Run the project's test suite for the affected view. Try in order:

1. `bundle exec rspec spec/views/<path>` if rspec + spec/views exists
2. `bundle exec rspec spec/system/<resource>_spec.rb` for system tests
3. `bundle exec rails test test/views/<path>` for minitest
4. If no tests exist for the view, do a syntax-check on the new view class:
   `bundle exec ruby -Iapp -c <path_to_view_class>.rb`

**If tests fail:**
- Revert the changes: `git checkout -- .` and `git clean -fd` (only in the affected
  subtree — never touch unrelated files)
- Mark the task as `- [!]` (failed) in fix_plan.md with a brief note
- Move to the next task — do NOT retry

**If tests pass:**
- Continue to Step 9.

### Step 9: Commit

Stage only the files this iteration touched and commit:

```bash
git add <list-of-specific-files>
git commit -m "retrofit: convert <relative/path> to Phlex"
```

Never use `git add .` or `git add -A`. Never amend a prior commit. Never skip hooks
(`--no-verify`).

### Step 10: Update the plan

Mark the task complete in `.phlexed/retrofit/fix_plan.md` by changing `- [ ]` to
`- [x]`. If the task spawned a new component, note the new component name inline.

### Step 11: Iterate

Return to Step 1 and pick the next task.

## Failure handling

- **Test failures:** see Step 8. Revert, mark failed, move on.
- **Missing registry component:** invoke `/phlexed-component` to create it, then
  continue the conversion.
- **Unresolvable helper / Rails dependency:** if a helper cannot be ported (e.g., a
  custom `content_for` pattern that breaks inside Phlex), mark the task as failed
  with `- [!]` and a note like "requires manual conversion: content_for :sidebar".
- **File has uncommitted changes:** skip and log. Do not touch uncommitted work.
- **Dependency cycle:** the audit should prevent this, but if one appears, skip both
  tasks and flag them for manual review.
- **3 consecutive failures:** stop the loop. Something systemic is wrong — the
  registry may be stale, the base class may be misdetected, or the project may use a
  non-standard convention. Report the pattern and wait for human input.

## What "complete" looks like

The loop is complete when every task in `.phlexed/retrofit/fix_plan.md` is either
marked `- [x]` (converted + committed) or `- [!]` (skipped, needs manual review).

After the last task, run these finalization steps ONCE:

1. Rebuild the registry: `phlexed-registry` (picks up any new components created
   during the retrofit)
2. Print a summary: total converted, total skipped, list of `.pre-phlex` files that
   can be deleted after user review
3. Report `STATUS: COMPLETE` with the counts

## Things you must NOT do

- Do not batch multiple view conversions in one commit
- Do not convert files that have uncommitted changes without asking
- Do not delete `.pre-phlex` backup files (the user does that)
- Do not edit `.phlexed/registry.json` directly — always via `phlexed-registry`
- Do not skip the test step, even for "obviously simple" views
- Do not use `--no-verify` or `--force` on any git command
- Do not retry failed conversions automatically — let the user decide
- Do not convert views in a batch whose prerequisites aren't complete
- Do not inline raw Tailwind classes when a registered component exists
- Do not drop accessibility attributes, data attributes, or semantic HTML
